# スキルは不変タグとGitHub Releaseからnpx skillsで配布する

Status: accepted

## 背景

Kakeai の制作スキル（`skills/kakeai-production/` と `skills/kakeai-composition/`）は、これまで利用者がリポジトリからエージェントランタイムのスキルディレクトリへコピーまたはシンボリックリンクして導入していた。この方法には次の問題がある。

- どのリポジトリ状態のスキルを入れたのか、利用者が後から特定できない。
- 更新が手作業で、Kakeai アプリの版とスキルの版の対応関係が残らない。
- 導入先のパスがランタイムごとに異なり、共有ワークスペースへ複製すると再現できない。
- スキルが要求する Agent Access 操作をアプリが公開しているかを、導入前に確かめる手段がない。

`skills` CLI は、Git の ref を指定した導入、`skills-lock.json` によるロック、エージェントディレクトリへの配置、ロックからの復元を提供する。Kakeai 独自の installer や lock 形式を作ると、この機能を複製し、CLI の変更に追随する保守負担だけが増える。

## 決定

1. **配布元は本リポジトリだけ**とする。スキルは GitHub Release と対になる `vMAJOR.MINOR.PATCH` 形式の不変タグからだけ導入する。`main` やその他の可変 ref を導入元にしない。
2. Git タグを Kakeai アプリとスキルの共通バージョンとする。初回公開版は `v0.1.0` とする。root・CLI・MCP の `package.json` は当面 `0.0.0` のままにし、リリース版はタグで識別する。
3. 導入・ロック・配置・復元は `skills@1.7.4` に委譲する。独自の installer や lock 形式を作らない。代表コマンドは次に固定する。

   ```sh
   npx skills@1.7.4 add shipwebdotjp/kakeai#v0.1.0 \
     --skill kakeai-production --skill kakeai-composition
   ```

4. プロジェクト導入では `skills-lock.json` を Git 管理し、`.agents/` は再生成対象として無視する。グローバル導入（`-g`）は `skills-lock.json` を作らない。
5. 更新は `skills update` で可変 ref に追従させず、新しい Kakeai タグを指定して同じ `add` を再実行する。これにより、常に公開済みの不変版をロックする。
6. ロックからの復元は `skills@1.7.4` の `experimental_install` を使う。この版に `install` コマンドはない。将来 CLI がコマンド名やロック形式を変えた場合は、固定版を上げる変更としてユーザーガイドと互換性履歴を同時に更新する。
7. 各公開タグについて、対応する Kakeai リリース、含まれるスキル、各スキルが必須とする正規の Agent Access 操作名、互換性上の注意を [スキル互換性履歴](../agent-access/skill-compatibility.md) に記録する。操作スキーマ、VisualTemplate の契約、ダイジェスト値は複製しない。
8. リリースは手動起動の GitHub Actions workflow で行う。版の形式、互換性履歴の当該版エントリ、型検査、全テスト、スキル発見を確認した後、同じコミットから注釈付きタグ `v<version>` と GitHub Release を作る。タグ作成後に検証をやり直さない。
9. リポジトリ設定で `v*` タグの更新と削除を禁止する。公開済みタグは不変であり、修正は新しいタグで行う。
10. `skills@1.7.4` の Node.js 要件に合わせ、リポジトリの Node.js 要件を `>=22.20.0` に揃える。root と `user-guide/` の `.npmrc` で `engine-strict=true` を有効にし、古い Node.js ではインストール時に失敗させる。`skills@1.7.4` はスキル発見確認のため root の固定開発依存に置く。

## Considered Options

- リポジトリからコピーまたはシンボリックリンクし続ける。→ 版の対応関係とロックが残らず、更新・復元が手作業のままになるため不採用。
- Kakeai 独自の installer と lock ファイルを作る。→ `skills` CLI が既に提供する配置・ロック・復元を複製し、ランタイムごとの検出先の変化に追随する負担が増えるため不採用。
- npm パッケージや skills.sh Pack として配布する。→ 配布チャネルが増え、Kakeai のリリースとの対応が二重になる。今回は対象外とし、必要になった時点で別 ADR にする。
- Kakeai アプリ内に導線を置く。→ スキルを利用するのは外部エージェントであり、アプリは実行時に `skills/` を読まない。今回は対象外とする。
- `main` から導入する、または `skills update` で最新へ追従する。→ 同じ導入コマンドでも内容が変わり、再現性とロールバック性を失うため不採用。
- GitHub Release の成果物だけを配布する。→ `skills` CLI は Git の ref を解決してスキルを取得するため、タグが必要になる。Release は人間向けの対として残す。
- タグではなくコミット SHA だけを指定する。→ 内容は不変になるが、人間がリリースを識別できず、互換性履歴との対応も読みにくいため、バージョンタグを採用する。

## Consequences

- スキルの導入と更新は、Kakeai の公開タグの作成と切り離せない。タグを打つ前に、型検査・テスト・スキル発見・互換性履歴の確認を終える必要がある。
- `skills-lock.json` は `skills` CLI の生成物であり、手で編集しない。新しいタグで `add` を再実行した差分をレビューしてコミットする。
- 既存の `Makefile` の `skill-install` ターゲットは正式な導入手段ではなくなるため削除する。旧来のコピー／symlink 手順をユーザーガイドの正式手順として残さない。
- スキルは引き続きアプリの実行時依存ではない。アプリは `skills/` を読みに行かず、スキルは MCP または CLI の公開操作だけを呼ぶ。
- 公開済みタグのスキル本文を修正するときは、既存タグを書き換えず、新しいパッチ版タグを切る。`v*` タグの更新・削除の禁止はこの運用の前提である。
- タグの作成後に GitHub Release の作成だけが失敗した場合、同じコミットから workflow を再実行すると、既存の注釈付きタグがそのコミットを指していることを確認したうえで Release の作成だけを再試行する。別のコミットを指すタグや注釈なしのタグが残っている場合は停止するので、タグを削除せず人間が原因を確認する。
- CLI や MCP の `--version` は `package.json` の `0.0.0` を返し続ける。利用者向けのリリース識別は Git タグと GitHub Release で行う。
- `skills` CLI の固定版を上げるときは、`add` / `experimental_install` のコマンド名、`skills-lock.json` の形式、Node.js 要件を確認し、ユーザーガイドと互換性履歴を同じ変更で更新する。
- 初回の `v0.1.0` は、この変更を `main` へ取り込んだ後に release workflow から作成する。手作業でタグだけを先に作らない。
