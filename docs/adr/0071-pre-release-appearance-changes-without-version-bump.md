# 正式リリース前は見た目・既定値の変更を版の追加なしで行う

Status: amends ADR-0061

`1.0.0` に達するまでの開発段階では、VisualTemplate の見た目・レイアウト・入力の既定値を変えるとき、既存の `id@version`（現行は `@1`）を書き換えてよい。再解釈を伴う場合でも版を追加しない。[ADR-0061](0061-template-version-as-reinterpretation-boundary.md) が定める「保存済みの有効入力を再解釈するなら版を上げる」境界は、`1.0.0` 以降に適用する。

理由は、開発段階の保存済み作品は利用者の資産ではなく検証用データであり、既定値の変更（例: 端末クロームの既定オン）のたびに新版を切り過去版の描画コードを維持するコストが見合わないため（[ADR-0034](0034-destructive-changes-before-1-0.md) の判断を、ADR-0061 の再解釈境界より優先する）。境界はアプリのバージョン番号またはリリースタグ（`1.0.0`）で判定する。

## Considered Options

- 再解釈を伴う既定値の変更でも `@2` を切る。→ 正式リリース前の見た目の試行錯誤ごとに過去版の描画コードを保守することになり、探索コストが過大なため不採用。
- 既定オンを避け、任意入力（既定オフ）で互換を保つ。→ クロームが既定で見えず、正式リリース前に望ましい見た目を既定にできないため不採用。
- リリース境界を設定やフラグで持つ。→ 単一の個人用アプリでは版番号で足りるため不採用（[ADR-0034](0034-destructive-changes-before-1-0.md) と同じ）。

## Consequences

- 開発段階では、テンプレートの描画・既定値・入力スキーマの変更を、版の追加なしで行える。既存の保存済み作品は、変更後に見た目が変わる、または作り直しが必要になる場合がある。これを互換性の欠陥として扱わない。
- 入力の追加自体は従来どおり任意フィールドとして行い、既定値は契約（`.default(...)`）で明示する。
- `1.0.0` のリリース時に、その時点の最新テンプレート版と `schemaVersion` を凍結する。以降の変更は版追加または移行で行う（[ADR-0061](0061-template-version-as-reinterpretation-boundary.md)）。
