# YouTube連携は読み取り専用とし、コメントソースを差し替え可能にする

> amended by [ADR-0123](./0123-live-youtube-local-llm-only.md): 実YouTubeのコメント処理はローカルLLMに限定し、外部LLMへ送らない。
> amended by [ADR-0128](./0128-live-comment-polling-primary.md): v1のコメント取得はlistポーリングを正規経路とし、streamListはスパイク後に判断する。
> amended by [ADR-0129](./0129-youtube-api-key-first-auth.md): 認証はAPIキーを第一候補とし、OAuthをフォールバックとして残す。

Status: accepted

ライブ配信のv1では、YouTubeのチャットを**読むだけ**にする。配信の作成・開始・終了、タイトル・サムネイル設定、チャット投稿、削除・ピン留め・モデレーションは人間が行う。アプリはコメントを取得してライブの進行に使い、AIの返答はステージの音声と字幕として出す。YouTubeへの書き込みは行わない。

## Context

- YouTube Live Streaming APIのチャット読み取りは、既定のクォータ内で30分の配信に十分収まる。書き込みを加えるとOAuthスコープ、権限、誤投稿・炎上のリスク、モデレーションの設計が増える。
- 配信の作成・開始・終了は、YouTube Studio、OBS、YouTubeのチャットUIで人間が行える。v1でアプリが代行する必要性が低い。
- AIの返答は配信の音声と字幕で視聴者に届く。チャット欄にも同じ文章を出すことはv1の価値に対して必須ではない。
- テストモードでは、YouTubeに接続せず、擬似コメントを同じパイプラインへ流す必要がある。HTTPそのものをモックすると、本番との差分が大きくなる。
- コメントの取得方法は、`liveChatMessages.streamList`と`liveChatMessages.list`のポーリングで異なる。実行環境によっては`streamList`がNode/RESTから使いにくい可能性がある。

## 決定

- OAuthスコープは `https://www.googleapis.com/auth/youtube.readonly` のみを使う。ライブチャットと、`liveChatId`解決のための配信メタデータだけを読む。
- アプリは次のWrite APIを呼ばない。`liveBroadcasts.insert` / `update` / `transition`、`liveChatMessages.insert` / `delete`、チャットのモデレーション、動画・サムネイル・タイトルの更新。
- 配信の開始・終了、タイトル・説明・サムネイル・公開範囲、チャット投稿、チャットの削除・ピン留め・ブロックは人間が行う。
- コメントの供給元は**コメントソース**の境界で抽象化する。
  - `youtube`: `liveChatMessages.streamList`を第一候補とし、接続断はバックオフで再接続する。`streamList`が使えない場合は`liveChatMessages.list`の5秒ポーリングへフォールバックする。
  - `fixture`: テスト用の擬似コメント。`{ atMs, author, text, kind? }`を指定速度で流す。
- テストモードではコメントソースだけを差し替え、フィルター、アナリスト、ディレクター、TTS、ステージ、コンソールは本番と同じものを使う。
- AIの返答はステージの音声と字幕に出す。YouTubeチャットへのテキスト投稿はv1では行わない。
- 将来、チャット投稿や配信操作を追加する場合は、新しいOAuthスコープ、誤投稿の防止、モデレーション、監査を含む別ADRで判断する。

## Considered Options

- AIの返答をYouTubeチャットにも投稿する。→ `liveChatMessages.insert`と書き込みスコープが必要になり、誤投稿・連投・炎上のリスクとモデレーションの設計が増えるため、v1では不採用。
- アプリから配信を作成・開始・終了する。→ YouTube StudioとOBSで人間が行えるうえ、配信状態の同期・失敗時の復旧・権限の設計が増えるため、v1では不採用。
- YouTubeのHTTP APIをモックしてテストする。→ モックと本番の差分が大きく、`streamList`のストリーミングや再接続の挙動を再現しにくいため不採用。コメントソースの境界で差し替える。
- 最初からポーリングだけにする。→ 実装は単純だが、`streamList`が使える場合の低遅延・低リクエストの利点を捨てるため、第一候補にはしない。フォールバックとして残す。
- アプリがYouTubeのモデレーションも行う。→ 権限と誤操作のリスクが大きく、v1の価値に対して過剰なため不採用。

## Consequences

- 配信の開始・終了、チャット投稿、モデレーションは人間の作業として残る。当日のオペレーターがYouTube Studioとコンソールの両方を見る運用になる。
- チャット欄だけを見ている視聴者には、AIの返答テキストは届かない。配信の音声と字幕が主経路になる。
- OAuthの設定とレビューが単純になる。`youtube.readonly`だけなので、誤投稿の事故を構造的に防げる。
- テストモードは、YouTubeの接続なしでコメントソースからステージまでを通せる。実YouTubeの読み取りは、別の受け入れテストとして行う。
- `streamList`がNode/RESTから使えない場合に備え、ポーリングのフォールバックを同じ境界の下に持つ。30分・5秒ポーリングは既定クォータに収まる。
- 将来、チャット投稿や配信操作を追加するときは、スコープと権限の再設計が必要になる。
