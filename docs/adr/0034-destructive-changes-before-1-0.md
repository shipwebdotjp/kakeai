# 正式リリース前はテンプレート版とschemaVersionの破壊的変更を許容する

アプリのバージョンが `1.0.0` に達するまでの開発段階では、VisualTemplate の `id@version` と ContentDocument の `schemaVersion` の両方について、破壊的変更を許容する。見た目・レイアウト・入力スキーマを変えるときは既存の版を書き換えてよい。`schemaVersion` を上げるときも、保存済みデータを作り直す前提とし、旧版の読出し解釈や移行関数を先回りして持たない。

`1.0.0` 以降は、[ADR-0009](./0009-template-version-immutability.md)/[ADR-0018](./0018-template-version-gc.md) のテンプレート版不変の規律と、[ADR-0013](./0013-content-schema-version-starts-at-1.md)/[ADR-0029](./0029-content-document-v3-visual-cue.md) の `schemaVersion` 移行の規律へ戻る。境界はアプリのバージョン番号またはリリースタグ（`1.0.0`）で判定する。

理由は、開発段階では保存済み作品が利用者の資産ではなく検証用データであり、テンプレートの見た目を変えるたびに新版を切り過去版の描画コードを維持するコストが見合わないため。表現の探索を止めず、正本データの意味を確定させるのは正式リリース時点に寄せる。破壊的変更を許容する代わりに、開発段階の保存データはアップグレード互換を保証しないことを明示する。

## Considered Options

- 開発段階でもテンプレート版を必ず追記する。→ 見た目の試行錯誤のたびに過去版の描画コードを保守することになり、探索コストが過大なため不採用。
- `schemaVersion` は従来どおり移行関数を必須にする。→ 実在しない開発用データの移行コードを保守することになり、[ADR-0013](./0013-content-schema-version-starts-at-1.md) の「移行コードを先回りして持たない」方針と重複するため不採用。
- リリース境界を設定やフラグで持つ。→ 単一の個人用アプリでは版番号で足り、余分な状態を持つ必要がないため不採用。

## Consequences

- 開発段階では、テンプレートの描画・入力スキーマの変更、および `schemaVersion` の破壊的変更を、版の追加なし／移行関数なしで行える。
- `1.0.0` のリリース時に、その時点の最新テンプレート版と `schemaVersion` を凍結する。以降の変更は版追加または移行で行う。
- 開発段階で保存した作品は、テンプレート・スキーマ変更後に読めない、または作り直しが必要になる場合がある。これを互換性の欠陥として扱わない。
