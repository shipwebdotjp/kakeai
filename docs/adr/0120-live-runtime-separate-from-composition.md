# ライブ配信はコンポジションとは別の状態駆動ランタイムとし、ライブパッケージで受け渡す

> amended by [ADR-0126](./0126-live-material-cards-static-or-mp4.md): 素材カードはコンポジションHTMLのiframeではなく、静止PNG/HTMLまたは短い無音MP4に限定する。

Status: accepted

Kakeaiのコンポジションは、音声テイクの尺から全体のタイムラインを解き、文書全体を1枚のHTMLへコンパイルする。ライブ配信は、台本の途中でコメントを拾い、TTSを生成し、音声を途切れさせずに表示を更新し続ける必要がある。両者は実行モデルが異なるため、ライブをコンポジションの延長として実装せず、別の状態駆動ランタイムとし、Kakeaiから**ライブパッケージ**を書き出して受け渡す。

## Context

- コンポジションのScene尺は、選択済みAudio Takeの尺から解決する。1行を追加すると以降の全行の開始時刻が変わり、全体の再コンパイルが必要になる。
- プレビューはコンパイル済みHTMLをプレイヤーへ差し替える。編集プレビューでは直前のHTMLを保持してプレイヤーの再生成を避けているが、秒単位の更新を前提にした仕組みではない。
- ライブでは、現在の発話が終わる前に次の音声を用意し、字幕・表情・素材・コメントを状態として更新する。全体タイムラインの再計算やプレイヤーの再生成を挟むと、画面の停止や音声の途切れになる。
- Kakeaiのテーマ、キャラクター画像、顔レイヤー、字幕、素材カードの見た目は価値があり、ライブでも同じ見た目を使いたい。ただし、コンポジションのScene・Cue・トランジション・プレイヤーをそのまま使う必要はない。
- ライブはKakeaiのDBを直接読まず、書き出し時点のスナップショットで動く方が、再現性・障害分離・別マシンでの実行に有利である。
- 同一モノレポで開発するが、実行プロセスは分ける。Kakeaiの単一プロセスAPI・workerにライブの常時接続や音声再生を同居させない。

## 決定

- ライブの実行系を `apps/live` として追加する。Kakeai本体（`apps/api` / `apps/web`）は制作と書き出しを担当し、ライブの進行には関与しない。
- Kakeaiは**ライブパッケージ**を書き出す。内容は、マニフェスト、ショープロファイル、テーマCSS、キャラクター定義と素材、事前コンパイル済みの素材カードHTML、準備済み音声、テストfixtureである。
- ライブパッケージは不変のスナップショットとし、実行時にKakeaiのDBを読まない。DBは共有しない。
- ステージは1920x1080の固定キャンバスを持つ状態駆動のHTMLページとする。左右のキャラクター、中央の素材カード、字幕、コメントカード、セグメントラベルをスロットとして描画する。HyperFrames Playerは使わない。
- ステージとコンソールはローカルWebSocketで接続し、サーバが`StageState`を送り、ステージが`audio_ended`などのイベントを返す。
- 素材カードは、単一Sceneのコンポジションを自己完結HTMLとして書き出し、中央スロットに`iframe`で埋め込む。ライブ実行時にコンポジションをコンパイルしない。
- 準備済みキューの音声は書き出し時に生成する。コメント応答の音声は実行時にTTSアダプタを直接呼んで生成する。TTSアダプタの実装は共有パッケージへ切り出し、KakeaiのJob APIをライブの即時生成に使わない。
- 見た目は、テーマCSS、キャラクター素材、字幕スタイル、素材カードとして共有する。ライブの進行には、コンポジションのタイムライン・Scene・Cue・トランジション・プレイヤーを使わない（素材カードとしての単一Scene表示を除く）。
- ライブのログと生成音声は、パッケージとは別の実行ディレクトリへ書く。KakeaiのDBへは書き込まない。

## Considered Options

- コンポジションのコンパイラとプレイヤーにライブモードを追加する。→ 全体再コンパイル、プレイヤー再生成、タイムラインの再計算が避けられず、ライブの連続更新に向かないため不採用。
- シーンやブロック単位のコンポジションを連続再生する。→ ブロック境界の継ぎ目、音声同期、応答ごとのコンパイルが必要になり、v1の複雑度が高いため不採用。将来、見た目を優先する場合の候補にはなる。
- ライブ専用アプリを作るが、見た目も別に作り直す。→ デザインの二重管理とドリフトが起きるため不採用。テーマ・キャラクター・素材カードは共有する。
- ライブの実行系を既存の`apps/api`に同居させる。→ 常時接続、音声再生、コンソール、配信ログがAPI・workerの責務と混ざり、障害分離も悪くなるため不採用。
- KakeaiのDBをライブアプリから直接読む。→ スキーマ移行、同時書込み、実行マシンの分離に弱いため不採用。ライブパッケージを境界にする。

## Consequences

- 実行系が2つになる。Kakeaiは制作・書き出し、`apps/live`は演奏に集中する。
- ライブパッケージのスキーマとバージョン管理が必要になる。パッケージ内のファイル参照は相対URLで完結する（フォントは同じMacのローカルフォントを使う）。
- 見た目は共有できるが、コンポジションのコードは共有しない。素材カードは事前コンパイルし、ステージはライブ専用のレイアウトを持つ。
- TTSアダプタの実装を共有パッケージへ切り出す必要がある。KakeaiのTTS Jobの挙動は変えない。
- ライブのログはKakeaiのScriptVersionとは別に保存する。VOD用の台本化は将来の変換として扱う。
- コンポジションの完全な再利用を捨てるため、ライブ独自のステージテンプレート、コメントカード、状態機械を実装する必要がある。
- ライブパッケージの書き出しはCLIから始める。APIとUIは、書き出しの運用が固まってから追加する。
