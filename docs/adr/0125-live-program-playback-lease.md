# ライブの再生はprogramステージ1つがリースを持ち、イベントを冪等化する

Status: accepted

ライブの音声再生とキュー進行は、**programステージ1つ**が所有する。サーバはprogramステージに再生リースを発行し、コンソールのプレビューはミュート・イベント非送信とする。すべての再生イベントは実行・セッション・キュー・試行・連番で識別し、サーバは古いイベントや重複イベントを無視する。

## Context

- ライブのステージは、OBS用のブラウザソース、別のブラウザタブ、コンソールのプレビューiframeで同時に開かれ得る。
- 複数のステージが同じ音声を再生すると、二重音声になる。複数のステージが`audio_ended`を返すと、サーバのキューが二重に進む。
- ステージのリロードや再接続で、同じキューの`audio_ended`が遅れて届くことがある。イベントに世代・試行・連番がないと、古いイベントを現在の再生として扱ってしまう。
- コンソールのプレビューは、オペレーターが状態を確認するためのもので、音声を鳴らす必要はない。

## 決定

- サーバは`StageLease`を発行する。`leaseId`・`runId`・`sessionId`・`role`（`program`または`preview`）・`expiresAt`を持つ。
- programステージは1つだけリースを保持する。リースを持たないステージは再生イベントを送れない。
- コンソールのプレビューは`role: "preview"`で接続し、ミュート・イベント非送信とする。音声の監視はOBSまたはprogramステージ側で行う。
- `StageState.playback`は、`cueId`・`attempt`・`startedAt`・`audioUrl`を持つ。
- `StageEvent`は、`runId`・`sessionId`・`cueId`・`attempt`・`sequence`・イベント種別を持つ。サーバは現在の`attempt`と`sequence`より古いイベントを無視する。
- ウォッチドッグは`attempt`単位で動かす。古い試行のタイムアウトで現在のキューを進めない。
- programステージが切断した場合、リースは`expiresAt`までに失効する。オペレーターはコンソールから明示的にprogramを引き継ぐ。自動で別のステージをprogramに昇格しない。
- 再接続したprogramステージには、サーバが現在のキューと再生位置を送る。再開できなければ同じ`attempt`の先頭から再生し、古いイベントは無視する。

## Considered Options

- サーバー側で音声を再生し、ステージは映像だけにする。→ macOSの音声経路とOBSの取り回しが複雑になり、ブラウザの音声再生の利点を失うため、v1では不採用。
- ステージを正とし、サーバはイベントを受け取るだけにする。→ 複数ステージ・再接続・二重進行を防げないため不採用。
- コンソールのプレビューでも音声を鳴らす。→ 二重音声とイベント重複の原因になるため不採用。
- リースなしで、サーバが最初に接続したステージをprogramとみなす。→ 再接続やタブの増減で所有者が曖昧になるため不採用。

## Consequences

- 音声の再生主体が1つになり、OBS用ステージとプレビューの二重音声を防げる。
- 再生イベントの冪等化により、再接続・リロード・遅延イベントでキューが二重に進まない。
- コンソールのプレビューは映像確認用になり、音声確認は別経路になる。
- programステージの引き継ぎは明示操作になる。自動昇格はしないため、障害時はオペレーターの操作が必要になる。
- `StageState`と`StageEvent`の契約が増える。P1でスキーマを固定する。
