# ライブカードは型付き状態スナップショットとライブ専用DOMレンダラーで描画する

Status: accepted

ライブの中央スロットに出すネイティブカードは、動画用Visual Templateの再利用ではなく、**型付きのLive Card** と**状態スナップショット**として定義し、ライブ専用のDOMレンダラーで描画する。レンダラーはエディタのプレビューと `apps/live` のステージで共有し、Shadow DOMとキー付き差分更新を使う。HyperFramesのコンポジション、GSAPタイムライン、プレイヤーは使わない。

## Context

- [ADR-0126](./0126-live-material-cards-static-or-mp4.md) は、ライブの素材カードを静止PNG/HTMLまたは短い無音MP4に限定し、カード内のGSAPタイムラインを実行しないと決めた。これは実行時の安定性とセキュリティのための契約であり、ブラウザの表現力を制限するものではない。
- ライブでは、見出し、画像、箇条書き、グラフ、引用のようなシンプルなカードを、Cueごとに素早く切り替えたい。カードが出た瞬間の小さなアニメーションと、同じカードのままリスト項目を順に出す状態遷移が必要になる。
- 動画のVisual Templateは、`RenderContext`、`ContentDocument`、スキン、`lineIntervals`、コンポジションキャンバスに依存し、出力はGSAPタイムライン用の `AnimationItem` である。ライブのカード状態とは実行モデルが異なる。
- 動画とライブで見た目を完全に一致させる必要はない。テーマの雰囲気が揃っていればよく、ライブは中央スロットに合わせたシンプルなレイアウトにする。
- カードをiframe内のHTML/CSSで表示する案は、状態遷移のたびに再読み込みが必要で、キー付き差分更新やプレビューと本番の一致が難しい。

## 決定

- ネイティブカードは `headline`、`image`、`list`、`chart`、`quote` の5型とする。型ごとに内容スキーマを持つ。
- カードは `states[]` を持ち、各状態はその時点の内容の**完全なスナップショット**とする。差分パッチは持たない。
- Cueは `{ cardId, stateId }` の `cardRef` でカード状態を参照する。同じ `cardId` が続く場合はカードを維持して状態だけを更新し、`cardId` が変わった場合はカードを差し替える。
- カードの要素は安定したIDを持つ。レンダラーはキー付き差分更新を行い、追加・変更・削除された要素だけをアニメーションする。カード全体を作り直さない。
- カードは `enter` と `update` のアニメーション設定を持つ。プリセットは `none`、`fade`、`slide-*`、`scale-in` とし、グラフは `none`、`grow`、`draw` を持つ。全体タイムライン、シーク、Cue内の時間同期は持たない。
- レンダラーは `packages/live-cards`（実装時に追加）に置き、エディタと `apps/live` で共有する。`@kakeai/video` には依存しない。
- カードはホスト要素のShadow DOMに描画する。カードCSSはShadow Root内に注入し、テーマのCSS変数とフォントはホストから継承する。
- カード画像は `resolveAsset(assetId)` で解決する。エディタはアプリのURL、ステージはパッケージ相対URLを返す。
- パッケージは `packageSchemaVersion: 2` とし、`show.json` に `cards[]`、`cardAssets[]`、Cue / Segmentの `cardRef` を含める。カード画像は `kind: "card-asset"` としてmanifestに記録する。
- 動画用のVisual Template、`RenderContext`、`RenderedCue`、エフェクトエンジンは共有しない。共有するのはテーマトークン、純粋なヘルパー、カードの内容フィールドの語彙に限る。
- 自由なHTML/JavaScriptをカードとして実行しない。カードは型付きデータだけを受け取る。

## Considered Options

- 動画のVisual Templateをライブでもそのまま使う。→ `RenderContext`、スキン、`lineIntervals`、GSAPタイムラインに依存し、ライブの状態遷移に合わせるために各テンプレートへモード分岐が必要になるため不採用。
- カードをHTML/CSSにコンパイルし、iframeで表示する。→ 状態遷移のたびに再読み込みが必要で、キー付き差分更新とプレビューの一致が難しいため、ネイティブカードの本経路にはしない。取り込んだWork SceneのHTMLカードには引き続き使い得る。
- HyperFramesのコンポジションをカードとして埋め込み、ミニプレイヤーで再生する。→ 全体タイムラインとプレイヤーがライブの状態駆動と二重管理になり、ADR-0120/0126の境界を破るため不採用。
- すべてのカードをMP4に書き出す。→ 3〜5秒の固定尺、ループ、書き出しコスト、データ更新不可の制約があり、Cueごとの状態変更に向かないため不採用。
- カードを完全な自由HTMLとして保存する。→ 差分更新、状態参照、プレビュー、セキュリティの検証が難しくなるため不採用。
- カードを動画のContentDocumentのSceneとして持つ。→ Scene、行、音声、Visual Cueの制約がライブに残り、状態スナップショットとCue参照のモデルが崩れるため不採用。

## Consequences

- ライブカードのデータモデル、レンダラー、アニメーション、パッケージ契約を独立して育てられる。
- 動画とライブでカードの見た目は完全一致しない。テーマトークンとビジュアルガイドで雰囲気を揃える。
- カード型ごとに型付きスキーマ、レンダラー、アニメーション、パッケージ検証を追加する必要がある。
- エディタとステージで同じレンダラーを使うため、プレビューの一致を保ちやすい。
- 状態は完全なスナップショットなので、データは重複するが、差分計算と保存が単純になる。
- カードの状態遷移とキー付き差分更新のテストが必要になる。
- 発話に合わせた項目の逐次表示は、Cue内のタイミング契約として別途設計する。全体タイムラインは導入しない。
- 取り込んだWork Sceneは、従来のPNG/HTML/MP4素材カードとして `materials[]` に残し、ネイティブカードの `cards[]` と混ぜない。
