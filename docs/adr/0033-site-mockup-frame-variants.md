# サイトモックアップはフレーム型とし、variantの加算的追加を許容する

`scene.site-mockup@1` を、有名な投稿サイト・技術サイト・ブラウザの「ガワ」の中に利用者の画像・動画を収める**フレーム型**の複合ビジュアルとして追加する。中身は利用者の素材とし、投稿本文やメタ情報を構造化データから組み立てるフェイク投稿型は対象外とする（構造化入力は table/chart 系で扱う）。

- `variant` は `x`/`instagram`/`tiktok`/`youtube`/`github`/`qiita`/`zenn`/`note`/`stackoverflow`/`hackernews`/`reddit`/`pixiv`/`niconico`/`browser` を初期セットとする（日本語・技術系を主とする）。
- **`variant` への値の追加は `@1` 内で許容する**（加算的enum）。既存 variant の描画・レイアウト規約を変えない限り新版を切らない。既存 variant のガワ構成を変える場合は [ADR-0009](./0009-template-version-immutability.md) に従い `@2` を追加する。
- ロゴ・ワードマークは同梱せず、配色・レイアウトの**汎用スタイル**で「らしさ」を出す。必要なら利用者が持ち込んだロゴ素材を任意で重ねる。
- 順序として、まずサイトモックアップを出し、その後に table/chart 系へ進む。

理由は、device-frame の仕組みをほぼ流用でき追加コストが小さく、解説動画での視覚的な映えが大きいため。また、構造化データから投稿を組み立てる型は入力UI（リピータ）と検証が重く、table/chart と設計を共有した方が効率的なため分離する。商標の同梱を避け、汎用スタイル＋利用者素材に閉じることで、ライセンス確認を利用者側へ明確に寄せる。

## Considered Options

- フェイク投稿型（構造化データで投稿カードを描画）を最初に作る。→ 入力フィールドが多く検証・警告・UIが重く、table/chart と設計が重複するため後回し。
- プラットフォームごとに別テンプレート（`scene.x-post@1` 等）を切る。→ レジストリが肥大し、共通の枠レンダラが重複するため不採用。単一テンプレート＋`variant` enum を採用。
- 実ロゴ・ワードマークを同梱する。→ 商標・ライセンスの懸念があるため不採用。
- variant追加のたびに `@2` を切る。→ 既存描画を変えない加算的追加まで版を増やすのは過剰なため、加算的enum追加は許容する（この例外を本ADRに記録）。

## Consequences

- `variant` の追加は `@1` の入力スキーマに値を足す形になる。既存 variant の描画を変えないことをテストで担保する。
- device-frame と共通の「枠内に画面を収める」レンダラを抽出して共有する。
- `screen` は `nestedMedia` に限定する。任意 `NestedVisual` の埋め込みは将来の版で検討する。
